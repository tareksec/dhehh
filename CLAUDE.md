# Agent Rules (Claude Code)

These rules are mandatory for any AI agent working in this repository.

## Code map (owner request 2026-10-20)

- To find code, read `CODEBASE_MAP.md` first, then open only the module file in `docs/codebase-map/` for the area you work on, instead of scanning the repository. Skip the map when the task already names the files to change. The code wins when the map disagrees — fix the map.
- A change that adds, moves or removes a model, service, panel page, route, job, command or table updates the matching `docs/codebase-map/*.md` file (and its "Last checked" line) in the same commit.

## Release notes are part of every commit

- **Before any `git commit` / `git push`, write the release note first.** Add or update the entry in `CHANGELOG.md` describing the change (follow `docs/release-policy.md`: categorize as major, minor, patch, security, hotfix, or maintenance, with Added/Fixed/Security/Technical Notes sections). A commit without a matching CHANGELOG entry is not allowed.
- Also keep the working log in `UPDATE_NOTES.md` current — it describes what a pending commit contains, ending with the commit status line.

## Commit policy

- **New work is committed and pushed to a feature branch as part of the work (owner decision 2026-10-14).** When a piece of work is finished — code, tests, bilingual keys, `CHANGELOG.md` and `UPDATE_NOTES.md` done and the checks under "Verification before handoff" passing — commit it and push it to a feature branch, without waiting to be asked. This applies to this repository and to the website repository (`bhd4232/zamzamint-new-website-theme`), which has no rules file of its own.
  - **Branch name = the session's topic.** Name the branch after what the work is about, in lower-case English with hyphens, under `feature/` (for example `feature/nextjs-footer-starter`, `feature/reseller-return-charge`). Use the same topic name in both repositories when one task touches both. One topic per branch: follow-up work on the same topic goes to the same branch; an unrelated new topic gets its own branch, started from `main`. If the session's instructions already designate a branch, push to that one instead of inventing another.
  - **Never push or merge to `main` without the owner's explicit approval in the conversation.** Coolify deploys `main` on push, so the owner decides when it moves (see the error-isolation section: the branch's checks must be green first). A feature branch is not live.
  - Never force-push or rewrite history on a branch that was already pushed, and never commit secrets, `.env` files or throwaway databases.
- Never run destructive commands (`migrate:fresh`, broad seeders) against non-demo databases.

## Business rules

- Never invent demo/placeholder business rules — real rules only, gathered from the owner. External credentials (payment, SMS, WhatsApp, WooCommerce) are always admin-configurable encrypted settings fields; the owner plugs in keys.
- Storefront-visible content must be manageable from the Filament admin panel, never hardcoded in views.

## Instruction text goes in an ⓘ icon (owner request 2026-11-01)

Applies to **every screen and every new piece of work, in all panels** — ERP admin (`/admin`), IMS Office (`/office`), Investor portal (`/investor`), Reseller portal (`/portal`), Trade portal (`/trade`). Full plan, phases and the conversion procedure: `docs/info-icon-instructions-plan.md`.

- **The instruction / help / explanation text under a page title, subtitle, section heading or field label is never printed as a line of grey text.** It is written inside an ⓘ (information-circle) icon that shows the text on hover (tap on a touch screen), like the fields of Ads → Meta Ad Accounts. Every new task you write follows this — do not wait for the conversion phases.
- **Use only the shared helpers** (`App\Support\InfoTip`, registered in `AppServiceProvider`): `->infoTip(__('English text'))` on fields, infolist entries and `Section` (instead of `->helperText()` / `->description()` / `->hint()`); `InfoTip::heading($title, $text)` in `getHeading()` for a page; `<x-info-tip :text="__('English text')" />` in a custom Blade view. A text that depends on state is a closure (`fn (Get $get): ?string => …`); empty = no icon. Never add a new `hintIcon()->hintIconTooltip('…')`, `hintAction()` + help modal, hand-made tooltip, or `<p class="text-gray-500">` instruction.
- **Bilingual in the same commit.** The text goes through `__()` and into both `lang/en.json` and `lang/bn.json` (the bilingual rule above applies unchanged; no Bangla typed in PHP/Blade). The ⓘ then reads in Bangla or English with the panel's language.
- **Moving an existing text into an ⓘ: copy it exactly.** No shortening or rewording without the owner. Long texts stay long.
- **What stays visible** (not an ⓘ): live values and status built from the record or form state, validation errors, row data (`TextColumn::description()`, stat captions), callouts and notifications, modal confirmations and empty-table messages, sign-in/welcome greetings. Anything else you leave visible on purpose is marked `// info-tip:keep (reason)` on the line above or the same line.
- **Enforced:** `tests/Unit/InfoTipGuardTest.php` fails if a file gets more plain instruction text than `tests/Fixtures/info-tip-baseline.json` allows, or if an `->infoTip()` text is not inside `__()`. `php scripts/info-tip-audit.php` lists what is left (`--panel=trade`, `--file=…`, `--dynamic`, `--blocks`). After converting a screen, run `php scripts/info-tip-audit.php --write-baseline`.
- A change that touches a screen also runs `php artisan test --filter=InfoTip` and, for converted screens, is looked at in Bangla and English at 1366 px and 360 px (hover and tap).

## Delete = type the name, then Trash (owner request 2026-11-01)

Applies to every delete in every panel. Plan, phases and the list of models still to convert: `docs/delete-and-trash-plan.md`.

- **Pressing Delete never deletes at once.** The modal shows the record's name with a copy button and an input; Delete only goes through when the name is typed or pasted exactly. A bulk delete asks for the number of selected records. This is wired once for every Filament `DeleteAction`, `DeleteBulkAction`, `ForceDeleteAction` and `ForceDeleteBulkAction` (`App\Support\TypeToConfirmDelete`, registered in `AppServiceProvider`), so build a delete with those Filament actions and it comes for free. A hand-made delete action (for example "Move to trash") calls `TypeToConfirmDelete::apply($action, permanent: …)` itself. Never write a delete that skips it.
- **What a user deletes goes to Trash first.** A new model that users can delete uses `SoftDeletes` (unless the owner says it is a log or technical row, which stays a permanent delete) and gets a Trash page: `class TrashedThings extends App\Filament\Resources\Pages\TrashedRecords`, the `'trash'` page registered **before** `'view'` in `getPages()`, `TrashedRecords::linkAction(ThingResource::class)` in the list page's header actions, and `use App\Filament\Concerns\TrashFollowsDelete;` on the resource (Restore and Delete permanently follow `canDelete()` / `canDeleteAny()`; define `canDeleteAny()` whenever `canDelete()` is stricter than Filament's default). A row in Trash still holds its unique slug / name: code that checks or generates one uses `withTrashed()`, and code that looks a person up by phone / e-mail to **create** a record when none is found (checkout, import, lead conversion) uses `Customer::matchOrRestore()` / `Supplier::matchOrRestore()` (`RestoresFromTrashWhenTheyReturn`) so a customer in Trash is brought back instead of duplicated (sign-in and sign-up keep ignoring Trash), and a list, picker or checklist that strips global scopes (`withoutGlobalScopes()`) on a soft-deleting model adds `->withoutTrashed()` (see `tests/Feature/CatalogTrashTest.php`). A table inside a record (a relation manager, such as an order's payments) uses the trait `App\Filament\Concerns\HasTrashView` instead of a page: a "Trash (n)" button switches the table to the trashed rows. From Trash a record is restored or deleted permanently (which asks for the name again). A model whose delete or restore moves money or stock (vouchers, orders, payments) keeps its own restore logic: it never uses the generic page until its `restored` handling is written and tested.
- **The name shown is the resource's record title.** A resource whose records have no name-like column (`name`, `title`, a number, a code…) defines `getRecordTitle()` and `hasRecordTitle()` (see `StockPoolResource`), so the modal never falls back to "Label #id".
- **Tests that run a delete action pass the confirmation:** `callTableAction('delete', $record, data: ['confirmation' => $name])`, bulk: `data: ['confirmation' => (string) $count]`. Unit logic: `tests/Unit/TypeToConfirmDeleteTest.php`; flow: `tests/Feature/DeleteTypeNameAndTrashTest.php`.

## Error isolation (owner request 2026-10-08)

- One module's error must not take the whole app down. A new sidebar badge is written as `navigationBadge()` with `HasGuardedNavigationBadge`; a new widget uses `GuardsWidgetRendering`; anything else drawn on every page goes through `App\Support\ModuleGuard::run()`. `ModuleGuardTest` enforces the badge and widget rules.
- Caught errors are reported to Super Admins (Deploy Error Logs), never swallowed silently. Isolation is off in `local` / `testing`, so tests still see real errors.
- Migrations must also pass on MySQL 8.4 (`.github/workflows/mysql-migrations.yml`): name long indexes explicitly (64-character limit, `MigrationIdentifierLengthTest`). Coolify deploys `main` on push, so the branch's checks must be green before pushing to `main`.

## Test runs must never touch demo/dev data

- Running tests must NEVER refresh, reseed, or otherwise modify the demo/development database.
- **Always run tests as plain `php artisan test` (or `--filter=...`) with NO `--env` flag.** Verified 2026-07-05: `php artisan test --env=testing` bypasses `phpunit.xml`'s env overrides and runs `RefreshDatabase` against the real `database/demo.sqlite` (env=local, file cache) — wiping demo data. Plain `php artisan test` correctly uses the in-memory sqlite + array cache + testing env from `phpunit.xml`.
- Never run `demo:refresh`, `db:seed`, `migrate:fresh`, or any seeder as part of testing or verification. The only place demo refresh may execute is inside the test suite's own isolated-database test (`DemoDataSeederTest`), which must keep using a disposable database.
- If a test needs data, it creates its own records under `RefreshDatabase`; never rely on or mutate seeded demo data.

## Verification before handoff

- Run the affected test files plus the full `php artisan test` suite, and `npm run build` when frontend assets change.
